## Assessment

Ordinary local stereo playback should not need a powerful gaming desktop. FloorballDJ also performs decoding, effects, overlapping playback, waveform generation, library operations, and analysis. Those activities need resources, but the architecture should keep them from delaying a playback command.

At the reviewed baseline, every new voice opens a decoder and creates and initializes a new WASAPI output. Hotkeys and much of that setup execute on the WPF interface thread. The supplied ProBook capture subsequently confirmed costly work before playback and recurring output initialization; it did not establish physical audible onset or assign all delay to one cause. Current scoped improvements and the opt-in reuse prototype are distinguished in the status table above.

The user reports a delay on every key press, with most audio at 320 kbit/s, stereo, 48 kHz. The supplied capture recorded five MP3 and two WAV starts, 15 decks, 553 audio jingles and 698 slots. These digital provider timings are evidence for routing/setup work, not a measurement of perceived delay. Selected output/transport, physical onset and the effect of the updated build remain unconfirmed. Bitrate alone does not identify the codec.

The inspected desktop has an AMD Ryzen 9 7900X (12 cores/24 logical processors), approximately 32 GB installed memory (31.2 GiB reported), NVIDIA GTX 1080 Ti plus AMD integrated graphics, Windows 11 Home, and both NVMe SSD and SATA HDD storage. The review did not establish which GPU renders FloorballDJ or which disk holds the user's audio. The returned ProBook capture reports i5-10210U (4 cores/8 logical processors), about 16 GB RAM, Intel UHD/MX250, Windows 11 Home build 26200, a 256 GB SK hynix drive and Balanced power plan. Audio endpoint/driver/transport, media location and AC/battery context still need recording for comparable runs.

## Efficiency principles across hardware

- Reduce work for everyone: avoid repeated output initialization, redundant decoding, full-library scans per command, repeated serialization, and needless UI updates. Do not introduce model-specific code paths or tune the architecture to the ProBook's CPU, RAM, or driver.
- Protect playback deadlines on every supported machine. Background analysis, waveform preparation, scanning, export, and backup use bounded work queues and yield resources to playback. Slower hardware may take longer to finish an offline job; it should retain the same features and results while keeping playback responsive.
- Use bounded, conservative resource defaults, then evaluate whether safe adaptation to memory pressure, measured background load, and audio deadlines improves throughput. More CPU cores alone do not justify more concurrent decoders or scans. Validate adaptation on multiple hardware classes and keep it stable rather than constantly changing behavior.
- Keep caches disposable, byte-bounded, and recoverable on misses. Stronger machines may benefit from additional preparation capacity, but correct playback must not depend on a large cache or powerful GPU.
- Preserve audio quality, effects, fades, visual feedback, and controls. Do not automatically disable features, lower audio quality, or require users to configure a special mode to make ordinary playback responsive.
- Measure the shared workloads on a range of machines: weaker and ordinary laptops, integrated graphics, different storage and audio devices, and the stronger desktop. The ProBook contributes evidence to this matrix; it does not define the product's minimum hardware requirements or its performance ceiling.

### Hotkey-to-audio path at the reviewed baseline

```text
WPF key event
  -> MainWindow: focus rules, reserved commands, shortcut/profile scans
  -> optional deck/page change, random-pool selection, or autoplay library refresh
  -> MainViewModel.Play / PlayCore
  -> AudioEngine.Play, largely inside the engine lock
       -> cleanup and matching-voice decisions
       -> open AudioFileReader
       -> schedule seek, create pitch/effect/gain/meter providers
       -> resolve endpoint, create WasapiOut, initialize output, start output
       -> start incoming ramp and outgoing fades
  -> output thread: first read, pending seek, decode, DSP, audio buffer
  -> Windows audio endpoint/device
```

The ordinary jingle path calls the engine synchronously. The engine lock encloses file/decoder/output setup. Autoplay shortcuts have an additional dependency: `ActivateAutoplayAsync` awaits `RefreshAvailableAsync` before loading and starting the playlist.

## Phase 2 — make audio output long-lived

Implementation status, 4 October 2026: [a stopped-output reuse prototype is implemented](PERFORMANCE-PHASE2-OUTPUT-REUSE.md). It retains at most two reset outputs for 30 seconds, matched by actual endpoint, route and source format, while preserving independent voices and their DSP. In the repeated 1,001-start desktop silent-WAV comparison with the corrected resources-only runner, output initializations fell from 1,001 to one and repeated handler-to-first-provider-buffer p95 from 15.936 to 1.612 ms. It is opt-in with the existing per-voice path retained for comparison. A shared completion guard fixes a cleanup/callback race found during testing. This initial step does not implement a mixer, prepared-reader cache or command queue, and does not qualify ProBook benefit, physical onset, device/sleep recovery or sustained resource use. Phase 2 remains open.

Prototype this early if F1 dominates repeated-start traces, especially on weaker hardware. It is likely the largest architectural improvement, but it has more audio-regression risk than indexed input or bounded background jobs.

1. Introduce an output-session abstraction: initialize the selected endpoint once, keep a mixer/output ready during the match, and attach/detach voices. Route main and preview independently. Decide how shared physical endpoints are handled while preserving their separate controls and playback state.
2. Normalize voice formats to a chosen session format/channel mapping with explicit resampling. Test mixed sample rates, mono/stereo, and endpoint conversion. Do not assume all files or devices are 48 kHz stereo.
3. Prepare readers/decoded blocks on workers with documented COM ownership. Transfer immutable decoded data or use a bounded producer/ring-buffer design. The present FLAC provider explicitly avoids reading on one COM apartment and consuming on another: preserve that constraint. A generic `Task.Run(() => Play(...))` is not a complete redesign.
4. Use an ordered, bounded playback-command mechanism and generation IDs for profile/device changes. Preserve command ordering, repeated-click fade versus polyphony behavior, cancellation, natural completion, and preview routing. Retire decoders/outputs outside the callback.
5. Keep each voice's RC1 gain, pitch, EQ/compressor/limiter, fade, and meter ordering. The setting called master limiter currently enables limiting inside each voice's effects provider; moving it after the mixer changes the sound and is outside a behavior-preserving optimization. Capture mix/output comparisons before changing the pipeline.
6. Prewarm the output and likely clips after profile load. Preload current deck/hotkey clips and next queue/team/follow-up candidates within the memory budget. Do not decode an entire music library into RAM. Cache decoded source data separately from per-play effect/gain state; never share a mutable reader between simultaneous voices.
7. For deep FLAC starts, evaluate bounded decoded-start caches or versioned temporary PCM/indexed decoding. Preserve sample positions and original source files. Failed/stale cache entries must fall back correctly; loop/resume paths need the same treatment as initial play.
8. Derive buffer draining and timing from the negotiated output configuration. Current fades use a fixed 60 ms drain for the requested 50 ms output. Keep that safe behavior until new output timing is verified. Sweep requested buffer sizes only after setup overhead is addressed; smaller buffers are accepted only if the hardware/audio-device stress matrix stays glitch-free. Do not hard-code a buffer choice around one laptop's results.
9. Implement endpoint invalidation, change/unplug, idle/sleep recovery, and resource disposal. An always-ready session must have a measured battery/idle cost and recreate itself reliably.

NAudio's [version-pinned WASAPI implementation](https://github.com/naudio/NAudio/blob/v2.2.1/NAudio.Wasapi/WasapiOut.cs) performs initialization and playback-thread/buffer setup. Reusing an initialized session is an architectural proposal based on that lifecycle and FloorballDJ's call sites; its actual benefit must be measured with the installed version.

Acceptance: warm starts avoid endpoint/output initialization; cold cache misses still work; main/preview routing, gains, fades, polyphony, output recovery, and all completion rules pass. Compare the same profile/media on both machines and retain the old engine during the prototype for controlled comparison.

Keep audio callbacks free of blocking disk I/O, control-tree traversal, JSON serialization, and disposal. Replace broad locks only when ownership is clear; moving a lock is not enough.

This extraction makes the existing behavior testable and reduces coupling in `MainWindow`/`MainViewModel`. Class size alone is not a performance defect; the benefit comes from isolating work and deadlines.
