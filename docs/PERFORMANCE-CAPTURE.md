# RC1 performance capture

This is the capture tooling from the [performance roadmap](PERFORMANCE-ROADMAP-RC1-TO-1.0.md). It measures where time goes while the program is optimized. The same tools work across Windows x64 PCs; the ProBook is one test machine in that comparison. The current kit includes [hotkey/random-group indexing](PERFORMANCE-PHASE1-HOTKEYS.md), the [bounded waveform scheduler](PERFORMANCE-PHASE1-WAVEFORMS.md), [ordered saves with owned snapshots](PERFORMANCE-PHASE1-SAVES.md), [background import/file-management/XML metadata](PERFORMANCE-PHASE1-METADATA.md), [autoplay start before library refresh](PERFORMANCE-PHASE1-AUTOPLAY.md), [less repeated UI/volume work](PERFORMANCE-PHASE1-UI-WORK.md) and an [opt-in output-reuse prototype](PERFORMANCE-PHASE2-OUTPUT-REUSE.md). Match capture/build metadata when comparing kits.

Normal direct launches leave capture and output reuse disabled. **Capture.cmd** and **Silent-Benchmark.cmd** enable the reuse prototype. **Legacy-Capture.cmd** and **Legacy-Silent-Benchmark.cmd** use fresh output initialization per voice, with the same other changes and completion guard. Diagnostic launches preserve the per-voice decoding/effect/gain/fade pipeline, routing and profile format. This is a development build of RC1, not a new release or full performance qualification.

## Use the capture kit on either computer

1. Extract the entire `FloorballDJ-RC1-Performance-*.zip` folder to a writable location. The package includes the runtime; a .NET developer installation is unnecessary.
2. Close any running FloorballDJ instance. Double-click **Capture.cmd**. This opens the normal application with its normal license admission and profile storage. Select your test profile as usual. Normal edits and session counts can still save; use a copied test profile if you want a fixed comparison fixture.
3. Note the selected audio output and Windows output format, connected interface/headphones, whether audio is wired or Bluetooth, AC or battery, power mode, display scaling, media disk, and file extension. `hardware.json` supplies CPU/RAM/OS/GPU/storage/audio inventory before the app launches, but does not determine the active endpoint, DPI, media location, or transport. Add missing context separately. Keep the files/settings/output fixed for comparisons on each machine.
4. Try first play, repeated hotkeys, and mouse clicks. Stop/reset between starts: a second press on an already-playing jingle normally requests a fade-out, and is counted separately. Repeat while waveforms load, autosave occurs, or analysis/export runs. Record which scenario and feature were active; do not disable those features to produce a favorable result.
5. Close FloorballDJ normally. The capture window generates **report.md** and **report.json** inside a new **captures** folder. Keep that whole run folder, including events, session metadata, and hardware inventory. Each launch gets a unique folder.

For the next ProBook comparison, run **Legacy-Capture.cmd** and then **Capture.cmd** with the same profile/files/output/power settings and the same sequence of starts. Reverse the order in a second pair. Note audible changes and test preview, overlap, fades, pause/seek, loops and queue/follow-up behavior. The comparison launcher contains the previous hotkey/waveform optimizations; it isolates the output lifecycle, rather than comparing with the original published RC1.

For named scenarios and power context, run from PowerShell in the extracted kit:

```powershell
.\scripts\Start-PerformanceCapture.ps1 -AudioOutputs reuse -Scenario hotkeys-actual-profile -PowerSource AC -Notes 'Built-in wired output; 48 kHz stereo; 100% DPI; MP3 on SSD'
```

`Notes` contains exactly what you enter and is saved to hardware.json. Events avoid song titles, media paths, typed keys, profile content, and license data. Jingle IDs, extensions, source formats, primary/secondary routing, default/explicit endpoint selection, numeric clip-start/fade values, and profile counts are recorded. Hardware inventory includes model/device names, driver versions and the power plan. Review the folder before sharing it.

The script defaults to `-AudioOutputs legacy`; use `-AudioOutputs reuse` to select the prototype explicitly. Its idle output cache is limited to two reset outputs for 30 seconds, matched by route, endpoint and source format. Reuse does not require the same file, but expiry, incompatible formats or busy outputs can cause fresh initialization.

## Repeatable automated comparison

Double-click **Silent-Benchmark.cmd** for 1,001 synthetic hotkey starts with a generated silent 48 kHz stereo WAV, the existing minimum 30 ms start ramp, and approximately 250 ms spacing after preparation. It stops playback before each trigger and validates one successful start and first returned buffer per trigger. The first observation is separated from the next 1,000 repeats. Allow roughly five minutes, depending on device initialization time.

**Legacy-Silent-Benchmark.cmd** runs the same fixture with fresh outputs. Both launchers use the default 250 ms spacing. The recorded Phase 2 desktop pair instead used explicit `-SpacingMs 100`, identically on both paths:

```powershell
.\scripts\Start-PerformanceCapture.ps1 -Benchmark -AudioOutputs legacy -SpacingMs 100 -Scenario output-legacy
.\scripts\Start-PerformanceCapture.ps1 -Benchmark -AudioOutputs reuse -SpacingMs 100 -Scenario output-reuse
```

The current runner uses a resources-only WPF application, an isolated temporary profile and a hidden main window. It calls the actual shortcut handler but does not inject physical keys or render the visible cart. Bound controls can still prepare waveforms, and normal view-model/timer work can run. It uses the Windows default output. It explicitly suppresses production startup/license windows, so startup measurements belong in the manual application capture. Earlier runners could execute production startup alongside the fixture; repeat their automated figures with the corrected runner before using them as controlled baselines. It leaves an isolated temporary folder for inspection.

The real shortcut handler reads global modifier keys. The runner waits outside its measured interval while modifiers are held and records modifier waits/retries in benchmark.json. Avoid sustained modifier-key use or other heavy work when collecting a clean baseline.

Compare keyboard routing against direct engine setup and measure capture overhead in fresh, otherwise identical runs:

```powershell
.\scripts\Start-PerformanceCapture.ps1 -Benchmark -Scenario keyboard-on -Iterations 1001
.\scripts\Start-PerformanceCapture.ps1 -Benchmark -Scenario keyboard-off -Iterations 1001 -WithoutDiagnostics
.\scripts\Start-PerformanceCapture.ps1 -Benchmark -Scenario engine-on -Iterations 1001 -Route engine
```

The diagnostics-off control reports synchronous dispatch duration only. It cannot report first-buffer timing, CPU, or stage breakdown. Both dispatch measurements include the runner's invocation overhead; compare identical routes and settings and repeat the pair before claiming a difference. Capture-on runs add event collection, PCM scanning until a first signal, a background writer, and one-second runtime sampling. Continuous silence exercises the signal scan for the whole voice, unlike most ordinary music. Overhead is therefore workload-dependent.

Use a confirmed copy of a real file for decoder/seek comparisons:

```powershell
.\scripts\Start-PerformanceCapture.ps1 -Benchmark -Scenario mp3-start -MediaFile 'D:\Test Audio\example.mp3' -Iterations 1001
.\scripts\Start-PerformanceCapture.ps1 -Benchmark -Scenario flac-trim -MediaFile 'D:\Test Audio\example.flac' -StartSeconds 60 -Iterations 1001
```

Supplied media plays repeatedly at **-60 dB master gain**, which is quiet but not muted. Choose a start before the end of the file with enough remaining audio for the test. This isolated fixture does not apply your real profile's effects, output routing, queue settings, or fades; use manual capture for those cases. Its low gain can also prevent the first-signal threshold from being reached. First-buffer timings remain useful.

## Reading the report

- **HandlerReceivedToFirstBufferReturned** measures from the start of the managed handler until its voice first returns decoded/processed samples to the output consumer. **PlaybackRequestedToFirstBufferReturned** omits preceding input routing. Both omit earlier Windows/WPF input-queue wait and later speaker/device latency.
- **FirstDecodedFrames** is a marker at the decoder read boundary; its numeric value counts interleaved samples, not stereo frame pairs. **FirstSignalReturned** marks the first returned post-fader buffer containing a sample above 0.0001. It includes leading silence, gain/fade behavior, and buffer quantization. It is not a sample-accurate speaker timestamp.
- **FileOpen**, **EndpointResolution**, **OutputInitialization**, **SeekApplied**, **EngineLockWait**, and related stages separate setup work. Parent stage durations overlap their children; do not sum every row. **AudioProviderRead** is provider processing time, not a full WASAPI callback or negotiated buffer deadline.
- **OutputLifecycle** identifies the per-voice or reuse-prototype path. **OutputCreated** and **OutputReused** identify each prototype start's actual initialization/reuse decision; a reuse hit skips construction and initialization. **OutputRetained** and numeric **IdleOutputCount** mark cache returns in the raw events. No idle playback stream or prepared-reader cache is introduced.
- In revision **phase1-save-v1**, **SaveSnapshot** is owned graph capture on the UI/model owner's thread; **SaveSerialization** is worker JSON creation. Earlier revisions included JSON creation in SaveSnapshot. **SaveQueueWait** measures predecessor wait, **SaveSnapshotBytes** counts JSON bytes and **SaveSuperseded** identifies a captured pending autosave replaced before submission. The save summary separates completion, superseding and failure. Total save time includes queue/disk/revision work; these nested rows must not be summed.
- Updated kits also report **ShortcutIndexRebuild**, **RandomPoolMembership** and **RandomPoolFileValidation**. **RandomPoolSelectionAndPlay** includes nested playback, so it overlaps preparation/initialization. The corresponding member, follow-up and available counts are numeric events in `events.jsonl`; compare identical groups when interpreting these durations.
- **WaveformQueueDelay** and **WaveformDecode** separate admitted queue wait from decoding. Resource rows include active decoders, pending jobs, waiting admissions and cached peak bytes on state changes. Expected shared defaults are at most one decoder, 16 admitted jobs including the active one, and 32 MiB cached peak payload. Views/geometry/working arrays use additional memory. Cancellation is cooperative at read-block boundaries; existing native reads can take longer to return.
- Scenarios are grouped by source/route, extension/source format, output route, playback mode, initial seek position, effective fade-in, output lifecycle/new versus reused output, and first observed versus repeated jingle use. Repeated jingle use does not guarantee output reuse; first use of a new file can reuse a compatible output. Keep effects/settings fixed and record their context separately. First observed use does not prove a cold OS/disk cache. Inspect multiple fresh launches separately. The report labels low sample counts; p99 from a short exploratory run is not qualification evidence.
- Runtime values show CPU core equivalents, memory/allocation bytes, cumulative GC counts, handles and threads. One core equivalent means one logical processor fully busy. GC counts do not measure pause lengths. **DispatcherQueueDelay** is a periodic input-priority probe, not each key's true input wait.
- Fade-out and polyphony-limit actions are separate from successful starts. Input commands without playback may be ordinary typing, unmatched keys, search or other controls; this capture does not prove those commands were missed.
- A missing closing summary, lost events, a file-size cap, or truncated lines produces a warning. Re-run the same scenario with a complete capture before relying on its distribution. Diagnostics buffer up to 8,192 events, drop rather than wait when full, and stop at a 128 MiB event-file limit. Close and start a new capture for another run.

The next measurement work still needs your actual profile/media on the laptop and desktop, visible UI scenarios, a transient fixture with no leading silence, and digital/physical loopback for audible onset. CPU stacks, actual GC pauses, disk/driver scheduling and underruns need a suitable profiler/system trace when the timings point there. No broad performance or feature-equivalence qualification follows from the silent fixture alone.

## Developer commands

From the repository, build a portable kit with matching Release symbols:

```powershell
.\scripts\Build-PerformanceKit.ps1
```

No installer is replaced. Kits include `build.json` with the source commit, an uncommitted-changes flag, and app binary/symbol hashes; keep the matching kit with its measurements.

Run capture correctness checks:

```powershell
dotnet run --project tests/FloorballDJ.PerformanceSmoke/FloorballDJ.PerformanceSmoke.csproj -c Release -p:PerformanceSymbols=true
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/Test-PerformanceReport.ps1
```

Checks cover disabled-hook allocation, bounded queue/drop accounting, async/nested/concurrent command correlation, unchanged sample output/offsets/EOF, selected-deck and fallback duplicate-shortcut precedence, privacy, runtime probes, writer failure isolation, and the file-size cap. They begin behavior characterization; they do not cover every shortcut, focus, autoplay, team, random-follow-up or recovery scenario in the roadmap.

The current checks also characterize indexed routing through edits/reordering/replacement, cultures and duplicate IDs, live selected-member file checks, subscription disposal, random/category/direct priority, empty-pool fallback, repeated random fade-out and active-setup switching.

Waveform checks cover exact peak parity, shared consumers, block/orphan cancellation, bounded admission, visibility priority, 500 rapid replacements, byte/count LRU, failed/oversized results, stale-result protection and unload/reload. Collect just those checks with `--waveform-checks --output <folder>` on the benchmark runner. This controlled fixture reports work counts, not audio latency. In manual captures, also change tracks while peaks load and open/close full/detail waveform views; keep these scenarios separate from ordinary starts.

Output checks cover exact switching-provider bytes/EOF, independent active/preview leases, compatible formats/endpoints, retention/expiry/invalidation/failures, delayed completion/loop epochs and waiting for actual backend Reset completion. Quiet real WASAPI behavior checks run both paths for repeat/fade/Space/pause/seek/preview/polyphony/trim/natural completion/loop behavior. Collect them separately with `--output-reuse-checks --output <folder>`. These checks do not replace non-silent PCM/listening, actual-profile, codec, real device/sleep and long-session qualification.
